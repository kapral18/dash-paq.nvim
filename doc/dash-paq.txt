==============================================================================
1. Introduction                                        *dash-paq-introduction*

dash-paq.nvim adds lazy loading and an update dashboard to |vim.pack|:

  - plugin specs (cmd/event/ft/keys, dependencies,
    init/config/opts, build hooks) resolving to plain |vim.pack.add()|
    calls;
  - a tag-vs-branch version policy: release tags or default branch, per
    plugin;
  - an interactive dashboard (|:DashPaq|) adding drift, orphan,
    risky-pin, and breaking-change detection over vim.pack's own report.

|vim.pack| handles installation, updates, deletion, and its lockfile.

==============================================================================
2. Requirements                                        *dash-paq-requirements*

  - Neovim >= 0.12.4 (tested; |vim.pack| needs only 0.12).
    `:checkhealth dash_paq` warns below it.
  - `git` on PATH: install/update (`vim.pack` itself), version-policy/
    dashboard analysis.
  - No third-party Lua dependencies.

==============================================================================
3. Installation                                        *dash-paq-installation*

Bootstrap with |vim.pack.add()| like any plugin, then call
`setup()`: >lua
    vim.pack.add({
      { src = "https://github.com/kapral18/dash-paq.nvim", version = vim.version.range("*") },
    })

    require("dash_paq").setup({
      spec = {
        "nvim-lua/plenary.nvim",
      },
    })
<
`version` keeps you on tagged releases. While dash-paq.nvim is 0.x every
feature release is a new minor and a minor release can break, so
`vim.version.range("~0.N")` with the current minor (see the releases
page) stays on one line.

There is no `plugin/` directory: every command registers inside
`setup()`, called once from `init.lua`, during startup. It never
disables 'loadplugins' or takes over the native |load-plugins| step; it
follows |vim.pack.add()|'s own startup semantics.

`setup()` adds each startup plugin to 'runtimepath', then runs
`config`/`opts` — so `require()`/`:colorscheme` work — before the native
"load plugins" step sources `plugin/**` and `after/plugin/**`. A
deferred (`cmd`/`event`/`ft`/`keys`) plugin loads the lazy.nvim way once
triggered: `plugin/**`, `config`/`opts`, `after/plugin/**`.

  - Globals a `plugin/` file reads (e.g. `vim.g.loaded_netrw`), other
    |vim.pack.add()| calls, and 'runtimepath' edits: set them anywhere in
    `init.lua`; "load plugins" runs after it.
  - A deferred plugin pulled in early (a startup entry's dependency, or
    triggered from `init.lua` after `setup()` returns) follows the
    startup path: 'runtimepath', `config`/`opts`, `plugin/**` left to
    the native step.
  - An argv buffer's own event, or a `-c`/`+cmd` startup command,
    triggers loading like any post-startup trigger — `plugin/**`,
    `config`/`opts`, `after/plugin/**` immediately. Exception: inside a
    file Neovim is sourcing, `after/plugin/**` waits for |VimEnter|.
  - Resetting 'loadplugins', or starting with `--noplugin`, `--clean`,
    or `-u NONE`, skips `plugin/**` sourcing like a plain
    |vim.pack.add()|: startup plugins still land on 'runtimepath', run
    `config`/`opts`.
  - When a declared plugin's `src` changes between Neovim sessions,
    `setup()` preserves the old checkout beside `opt` as
    `<name>.backup-<id>` and installs the new `src`. It reports the backup
    path. If installation fails, it restores the previous checkout when
    the target path is free; otherwise it reports the backup for recovery.
    Restart to register a restored clone with `vim.pack`.
    Source strings must match exactly, as in `vim.pack`; use the same
    spelling in bootstrap calls and specs, including the `.git` suffix.

==============================================================================
4. Setup                                                      *dash-paq-setup*

                                                      *dash-paq.setup()*
`require("dash_paq").setup(opts)` — call exactly once; a second
call raises a Lua error. `opts` fields:

  `spec`        list of spec tables/strings (see |dash-paq-spec|).
  `modules`     list of Lua module names, each `require()`d, returning a
                spec or list of specs; splits config across files
                instead of one big `spec` list.

At least one of `spec`/`modules` is required; combine both if needed.
Remaining fields (`dashboard`, `version_policy`, `default_host`,
`hosts`, and `dev`) are covered in |dash-paq-config|.

==============================================================================
5. Spec fields                                                 *dash-paq-spec*

Each `spec` entry (or one returned from `modules`) is a string
(`"owner/repo"`) or a table, lazy.nvim-shaped. Specs resolving to the
same `name` merge field by field, not "last wins": `src`/`dir` keep the
first value, `opts` deep-merges, `dependencies`/`cmd`/`event`/`ft`/`keys`
union, `priority` takes max, `lazy = false` wins over `true`; every
merged spec's own `init`/`config` runs.

Supported fields:

  `src`/`[1]`      Git source: `owner/repo` (via `default_host`),
                   `scheme://` URL, `git@...`, or `gh:...`, verbatim.
  `name`           Explicit name; else `src`'s basename minus `.git`, or
                   `dir`'s basename.
  `dir`            Local directory onto 'runtimepath' when no `src` is
                   given (load order after the built-in `site` pack dir).
  `dev`            `true` loads from `dev.path .. "/" .. name` when
                   present; a string sets a per-plugin base dir instead;
                   see |dash-paq-dev|.
  `version`        `false` = branch tip; `"*"` = latest semver tag; a
                   `^`/`~`/`>`/`<`/`=` range = greatest matching tag;
                   other string = literal tag/branch/commit; omitted =
                   version policy decides (|dash-paq-version-policy|).
                   Across merged specs, `version = false` overrides
                   pins from other specs; otherwise the last pin wins.
  `commit`/`tag`/`branch`
                   Explicit pin; priority over `version`.
  `enabled`/`cond` Boolean or `fn(spec)`; any false among merged specs
                   disables it. A function that throws is reported and
                   counts as false.
  `optional`       Disabled unless at least one merged spec isn't
                   `optional`.
  `dependencies`   `owner/repo` strings or spec tables, loaded before
                   the entry; cycles silently cut.
  `init`           `init(plugin)`, at setup time, before install. As in
                   lazy.nvim, `init`/`build`/`config` get `plugin`: the
                   spec with `name` and the plugin's `dir` filled in
                   (`dir` is nil before the first install); `opts`/
                   `keys`/`cond`/`enabled` functions get the same
                   `plugin`, with `dir` once known.
  `build`          `fn(plugin)`, `":Ex command"` string, or shell command
                   (`/bin/sh -c`, plugin's path), on `PackChanged`
                   install/update. A deferred entry loads first so build
                   acts on the real plugin; during `init.lua` sourcing,
                   the load and build both queue to run once on
                   `VimEnter`.
  `opts`           Table (deep-merged across specs) or `fn(spec, opts)`
                   returning a replacement table.
  `config`         `fn(plugin, opts)`. With no `config` function,
                   `setup(opts)` auto-calls, only when a spec supplied
                   `opts` or `config = true`, on the first of: `name`,
                   `name` minus one `.nvim`/`.vim`/`nvim-`/`vim-`/
                   `.lua`/`-lua` affix, or `name` with `-` -> `_` —
                   whichever `require()`s and has a `setup` function.
                   If none does, it warns; if one fails to load, it
                   reports that error.
  `keys`           String, table, or `fn(plugin)` returning a key list;
                   entries: an lhs string, or a table with `lhs`/`[1]`,
                   `rhs`/`[2]`, `mode` (default `"n"`),
                   `ft`/`desc`/`expr`/`nowait`/`silent`, `noremap`/`remap`,
                   `enabled`. A known `rhs` becomes a real mapping on
                   load, any route. `lhs`-only: loads the plugin,
                   replays `lhs` into its own mapping, with the register
                   and count typed before it in Normal/Visual mode. In
                   `o` mode (also part of `""`) the load runs under
                   textlock, so that plugin's `config()` cannot change
                   buffers or windows.
  `cmd`            String/list of command names, deferring load until
                   first use; forwards `<bang>`/range/count/`<mods>`/args.
                   Before the first load a range is read as lines, so
                   marks like `'<,'>` work and a count must not exceed
                   the buffer's line count.
  `event`          String (`"BufEnter"`, or `"BufEnter *.lua"` with a
                   pattern), `{ event = "User", pattern = "Ready" }`
                   (`event` may be a list), or a list of these; defers
                   load until fired. An event Neovim does
                   not know is reported and skipped; the plugin loads as
                   if it were not set. After loading, the
                   event replays only in augroups that had no handler
                   for it before loading. Replay preserves the match
                   and buffer context; no augroup, no replay.
  `ft`             String or list of filetypes, deferring load.
  `lazy`           `false` loads at startup even when triggers are set;
                   `true` keeps it deferred with no trigger (loadable via
                   `require()`, `:DashPaq load`, or as a dependency).
  `priority`       Load order among non-deferred entries (default 50;
                   higher first; ties keep spec order). Values below 50
                   are clamped to 50.

In addition to `cmd`/`event`/`ft`/`keys`, a deferred entry also loads
the first time `require()` misses on a top-level module name it
provides (`lua/<name>.lua` or `lua/<name>/`) -- e.g.
`require("local-highlight")` loads a `local-highlight.nvim` entry even
before its own `event` trigger has fired. This is automatic, not an
opt-in spec field; a disabled entry is never loaded this way, and
|:DashPaq-trace| shows the reason as `require:<modname>`.
Shared namespaces select the first entry in dependency order that provides
the requested module. Linked Lua files and directories are supported.
A missing plugin or required dependency directory leaves its load triggers
available for retry. `require()` retries discovery when a missing Lua directory
becomes available.

Unsupported fields                                 *dash-paq-spec-unsupported*

Not read by dash-paq.nvim: `main`/`module`/`import`/`specs`/`pin`/
`submodules`/`url`. A spec with `import` is reported; list each
module it would import (e.g. `plugins.editor`) in `opts.modules` instead.
lazy.nvim's `VeryLazy` and LazyVim's `LazyFile` (bare or as `User`
patterns) are reported and skipped, since nothing fires them here; the
plugin loads as if they were not set. `event = "User"` with your own
`pattern` still works. Nested lists of specs are flattened.

6. Configuration                                             *dash-paq-config*

`opts.dashboard`, `opts.version_policy`, `opts.dev` each accept `false`
to disable, `true` for the defaults, or a table deep-merged over the
defaults below. `setup()`
warns once about unknown keys, values of the wrong type (those keep their
default), and hosts missing `compare` or `commit`. `opts.spec` and
`opts.modules` also accept a single string.

dashboard                                          *dash-paq-config-dashboard*
>lua
    dashboard = {
      height_ratio = 0.68,      -- window height fraction
      min_height = 18,
      margin = 6,               -- gap kept to editor edge
      refresh_on_open = true,   -- refresh online on open
      ascii = false,            -- true = no Nerd Font glyphs
      fast_scroll = true,       -- full redraws skip highlights past 120 rows
      fetch_concurrency = 8,    -- concurrent git fetch jobs
      apply_batch_size = 4,     -- plugins checked out per blocking update apply
      skip_risk_confirm = false,  -- skip confirm on breaking-flagged updates
      skip_clean_confirm = false, -- skip confirm on orphan cleanup
    }
<
`opts.dashboard = false` disables every dashboard command
(|dash-paq-commands|) except |:DashPaq-trace|/|:DashPaq-load|/|:DashPaq-toggle-dev|,
which belong to the loader.

version_policy                                *dash-paq-config-version_policy*
>lua
    version_policy = {
      min_tags = 3,
      commit_lag_multiplier = 1.5,
      max_commits_since_tag = 150,
      sparse_tag_threshold = 30,
      max_tag_age_days = 180,
      ttl_days = 3,             -- cache lifetime before recompute
      avg_window = 6,           -- tags averaged for release size
      startup_delay_ms = 200,   -- delay before startup refresh
    }
<
See |dash-paq-version-policy| for what each threshold gates.
`opts.version_policy = false` disables the policy: plugins with no
explicit `version`/`commit`/`tag`/`branch` track default branch.

default_host / hosts                                   *dash-paq-config-hosts*
>lua
    default_host = "https://github.com/", -- for "owner/repo" shorthand
<
`hosts` is merged over built-in `github.com`/`codeberg.org` entries
(both `{ compare = "compare/%s...%s", commit = "commit/%s" }`). Add a
host (both `compare` and `commit`) for its dashboard compare and commit pages;
an entry missing either field is dropped.

dev                                                      *dash-paq-config-dev*
See |dash-paq-dev|.

7. Commands                                                *dash-paq-commands*

Everything is a subcommand of one command, `:DashPaq`. Subcommand names
and their arguments complete with <Tab>.

:DashPaq[!]                                                         *:DashPaq*
Open the dashboard; repeated calls reuse the window. `!` closes an open
dashboard and opens a new one. Opening honors `refresh_on_open`: it
fetches only when enabled. Use `R` to refresh online or `r` offline.
`!` is rejected on every other subcommand.

:DashPaq sync                                                  *:DashPaq-sync*
Fetch remotes and open `vim.pack.update()`'s update confirmation.
Refreshes the cached report/version policy.

:DashPaq status                                              *:DashPaq-status*
Open the same update confirmation using local refs without fetching
(`vim.pack.update(nil, { offline = true })`). Confirming updates still
changes checkouts and the lockfile.

:DashPaq stats                                                *:DashPaq-stats*
Print last raw update/same/error counters, check timestamps.

:DashPaq trace [plugin]                                       *:DashPaq-trace*
Shows every enabled entry's load status, load reason, time loaded, and
trigger set in a buffer; filters to one plugin by name. `q`/`<Esc>`
closes it.

:DashPaq load {plugin}                                         *:DashPaq-load*
Force-load one deferred entry: dependencies, `config`/auto-`setup()`
(`init` ran at setup time), after/plugin files, as if triggered.

:DashPaq lock info                                             *:DashPaq-lock*
Show the lockfile path, plugin count, mtime.

:DashPaq lock export {path}
Copy the live lockfile to `{path}`. `{path}` may contain spaces.

:DashPaq lock import {path}
Overwrite the live lockfile from `{path}` after validating plugin names,
sources, revisions, and serialized versions. Restart afterwards:
`vim.pack` keeps the lockfile it read at
startup in memory, so any update or delete applied before the restart
(for example a confirmed |:DashPaq-sync| or |:DashPaq-status|, or the
dashboard's `u`/`U`/`<CR>`/`V`/`C`) writes that copy back over the
import. After the restart, plugins missing on disk install at
the lockfile's revisions, and
`vim.pack.update(nil, { target = 'lockfile' })` moves installed ones to
them. |:DashPaq-sync| instead updates each plugin to its spec's
`version`.

:DashPaq toggle-dev {plugin}                             *:DashPaq-toggle-dev*
Flip a dev-capable plugin between its upstream `vim.pack` clone and its dev
checkout, without the dashboard: to `upstream` when it currently uses a dev
checkout, else to the base's default dev checkout (|dash-paq-dev|).
It flips from the saved `dev.json` choice, so repeating it
before a restart toggles back. Warns when there is nothing to switch to
(no `src` for upstream, or no dev checkout). Takes effect on restart and
offers one; see |dash-paq-dev-toggle|. Works with `opts.dashboard =
false`. Completes dev-capable plugin names.

:DashPaq policy-rebuild [plugin]                     *:DashPaq-policy-rebuild*
Clear and recompute the cached tag/branch heuristic; a plugin name
rebuilds only it.

Buffer filetypes, e.g. for session-save exclusions: `dashpaq` (dashboard),
`dashpaq-details` (details popup), `dashpaq-trace` (|:DashPaq-trace|).

8. Dashboard keys                                    *dash-paq-dashboard-keys*

Buffer-local to the dashboard window:

  `q`/`<Esc>`      close the dashboard
  `gg`             jump to the first row
  `R`              refresh online (fetch)
  `r`              refresh offline (no fetch)
  `<Space>`/`x`    toggle selection (row, or visual range)
  `a`              select all visible; deselect them if all are selected
  `A`              clear selection
  `<CR>`           update cursor plugin, if pending
  `u`              update pending plugins among visible selections;
                   with no visible selection, use the cursor row
  `U`              update all visible pending
  `C`              delete selected plugins not in spec, else all of them;
                   confirm
  `V`              heal selected drifted plugins, else all drifted plugins;
                   re-checkout to declared version offline
  `o`              open the compare page of a pending update, else the repo
  `O`              open the repository
  `K`              open the details popup
  `L`              toggle a dev-capable plugin between upstream and a local
                   checkout (|dash-paq-dev|); saves the choice and
                   offers `:restart`
  `T`              open |:DashPaq-trace| for the row under the cursor
  `f`              cycle filter: all -> updates -> issues -> selected
  `s`              cycle sort: status <-> name
  `/`              search by name substring
  `c`              clear the search
  `?`              open the key-reference help popup

`C` and `V` include rows hidden by search or filters.

`<CR>`/`u`/`U` fetch in the background, confirm breaking changes against
the fetched targets, then check out each fetched
plugin with `vim.pack.update`, which blocks input while it runs. While
the cursor keeps changing lines, queued checkouts wait until it has
stayed on one line for 300 ms. The progress counter counts completed rows,
including checkouts. Applied counts include only confirmed successful
checkouts. Operations continue after closing the window; a new operation
waits for the previous one to finish.

Filter/search/sort state persists across sessions (see
|dash-paq-state|); a saved `selected` filter reopens as `all`.
Selection is not persisted: it starts empty each time the dashboard opens.

Details popup keys                                     *dash-paq-details-keys*
`K` opens: one line per pending commit (breaking-change markers), plus
the status in the title and its risk, reason, semver, signals, version,
source, repo, and compare page.

  `q`/`<Esc>`   close the popup
  `o`           open the commit under the cursor; elsewhere, as in the
                dashboard: the compare page of a pending update, else the
                repository
  `O`           open the plugin repository
  `r`           close the popup and refresh offline, as in the dashboard

Row statuses, by the words the dashboard shows: `update`, `up to date`,
`failed` (the check or update failed), `not checked`, `not in spec`
(installed, no longer declared), `drifted` (checkout no longer matches
the declared version), `non-release tag` (`version = "*"` would pick a
non-release tag over the latest real release), and `local` (a
|dash-paq-dev| override, never touched by `vim.pack`).

The window is as wide as the table plus a two-cell margin on each side
(narrower editors scroll it horizontally). The header keeps a fixed
height. Below a blank line it shows the title and the filters as pills,
the active one highlighted (`f` cycles them), and `press ? for help` on
the right. While an operation runs, a progress bar fills the next line.
Then a summary: `Total: N plugins` (`Showing: N of M plugins` while a
filter or search is active, the task progress while an operation runs)
and each non-zero status count with its icon; when the line is too wide,
counts drop their words from the right. Counts cover all
plugins. A dimmed line shows the last check time, sort, search, and
selection.

Below the header, the table titles its columns `Plugin`, `Version`, and
`Note`. Each row shows a selection box, the status icon, the plugin, its
version (`current -> target` for an update; a branch-tracking update
shows the target's tag, else its commit), and a note in words. An update's
note is its size (`minor release`/`patch release`, or `12 commits` when
either end has no version), `downgrade` when it moves to a lower version or
only reverts commits, or `possibly breaking`; other rows that need attention say
`drifted from spec`, `non-release tag`, `not in spec`, `failed`, or
`not checked`. `?`
lists what each icon means. Breaking signals come from versions and
commit messages, not compatibility tests.
Use |:DashPaq-stats| for the last check counts and check/apply times.

9. Version policy                                    *dash-paq-version-policy*

With no `version`/`commit`/`tag`/`branch`, the version policy decides
release tags or default branch tip. It caches the decision per plugin name
and source; a changed source invalidates the old decision. It stores these
under |dash-paq-state|, re-evaluating once per `ttl_days` (default
3), async after startup (`startup_delay_ms` after `VimEnter`, one plugin
per tick) or sync on |:DashPaq-sync|/|:DashPaq-status|/
|:DashPaq-policy-rebuild|. A decision takes effect at the next
startup's `setup()` call, not immediately; the first time a policy is
generated, dash-paq.nvim notifies "restart to apply tag pins". A policy
written by an older release is ignored and rebuilt the same way, with the
same notice.

With no semver-shaped tags, the policy selects `branch`. When the branch
tip is at the latest tag, it selects `tags`.

With fewer than `min_tags` tags, it selects `branch` only when commits
since the latest tag exceed `sparse_tag_threshold`; otherwise, `tags`.
This ends evaluation: the ratio, age, and cap checks do not apply.

With at least `min_tags` tags, it selects `branch` when any of these holds:

  1. Commit-ratio (`commit_lag_multiplier`/`avg_window`):
     commits since the latest tag exceed a recency-weighted average
     commits-per-release over the last `avg_window` (floor 3) tags,
     times `commit_lag_multiplier`.
  2. Tag-age (`max_tag_age_days`): the latest tag is older than
     `max_tag_age_days` and a commit has landed since.
  3. Absolute-cap (`max_commits_since_tag`): commits since the latest
     tag exceed `max_commits_since_tag`.

Otherwise, it selects `tags`.

A `tags` decision resolves to a caret/tilde range from the latest release
tag: `^MAJOR.0` for `MAJOR >= 1`, else `~0.MINOR`. `vim.pack` then resolves
the greatest matching tag itself on every install/update. Prerelease tags
are skipped, since a range built from one matches no tag.

Defaults: |dash-paq-config-version_policy|. Tag parsing is strict
MAJOR.MINOR.PATCH semver (matching `vim.pack` 0.12.4's own resolution);
two-part tags like `nvim-0.6` never beat a real `vX.Y.Z` tag.

10. Local development (dev)                                     *dash-paq-dev*

`opts.dev` loads a plugin from a local checkout instead of its
`vim.pack` clone, for iterating on your own plugin.
>lua
    dev = {
      path = "~/projects",   -- base dir; plugin resolves to path .. "/" .. name
      patterns = {},      -- Lua patterns matched against plugin name
      fallback = true,    -- fall back to normal src when the dir is missing
    }
<
An entry is a dev entry when `dev = true`, `dev` is a non-empty string, or
its name matches `dev.patterns`. The last explicit `dev` value wins across
merged specs; `dev = false` opts out even when the name matches a pattern.

Base dir: a string `dev` is that path (`~` expanded), overriding
`dev.path .. "/" .. name` for that one plugin; `dev = true`/a pattern match
uses `dev.path .. "/" .. name`.

The base is then resolved:

  - Base has its own `.git` dir (a normal clone), or a `.git` *file*
    (a linked worktree's `gitdir:` pointer) that does not resolve to a bare
    repo: loads the base itself, as a git work tree.
  - Base has no `.git` but an immediate child directory does, or its `.git`
    file resolves to a bare repo (a `.bare`-backed worktree layout: a
    "container" of worktrees either way): loads the worktree on the
    repository's HEAD branch, else the first non-bare `git worktree list`
    entry.
  - Base exists and isn't git at all: loads the base itself, unchanged.
  - Base missing, or an existing directory with no plugin content (none
    of `lua/`, `plugin/`, `after/`, `ftplugin/`, `colors/`, `doc/`, ...):
    `fallback = true` (default) warns and loads normally from `src`;
    `fallback = false` disables the entry with an error. An entry with
    no `src` is disabled with an error either way.

Either way it loads from that directory onto 'runtimepath', not an
installed/updated `vim.pack` clone, and the dashboard shows it as `local`.
`opts.dev = false` disables dev resolution entirely.

Toggling upstream/dev checkouts                          *dash-paq-dev-toggle*

In the dashboard, `L` on a dev-capable plugin's row (see
|dash-paq-dashboard-keys|) offers every checkout for that plugin:
`upstream` (only when the spec also has a `src`) plus every worktree of a
git base, or the base itself for a non-git one. Two choices flip directly;
three or more open a picker. The choice is saved to `dev.json`
(|dash-paq-state|) and takes effect on the next `setup()` call — no
live reload (`vim.pack.add` runs once at startup, and re-sourcing an
already-loaded plugin's files/config isn't safe in general) — so `L`
offers a `:restart` afterward. A saved choice is honored only when it names
one of the base's *current* candidate checkouts; a deleted worktree, a
plugin whose spec dropped `src`, or an existing directory that no longer
matches the base's candidates (e.g. after the spec's `dev` base changed) is
ignored with a warning and falls back to the default above.

|:DashPaq-toggle-dev| switches upstream <-> the default dev checkout.
`L` can pick a specific worktree. Both use the saved choice, so repeating
a switch before restarting changes the pending choice.

A switch to upstream is refused with a warning, and nothing is saved, when
the installed clone is not a plugin directory or has none of the top-level
Lua modules the dev checkout provides (for example a rename that upstream
does not have yet): update the clone or push upstream first. A clone that
is not installed yet is not checked; the restart installs it.

11. Health                                                   *dash-paq-health*

`:checkhealth dash_paq` checks:

  - `setup()` has been called.
  - Neovim >= 0.12.4 (warns below; see |dash-paq-requirements|).
  - `vim.pack` is available.
  - `git` is on PATH.
  - |dash-paq-state| dir exists and is writable.

12. State files                                               *dash-paq-state*

Under `stdpath("state") .. "/dash-paq/"`:

  `version_policy.json`   per-plugin source, strategy, latest tag, reasoning
                          (schema 4; see |dash-paq-version-policy|).
  `dashboard_state.json`  last update report (per-plugin status, pending
                          commits, diff URLs), timestamps/counters,
                          filter/sort/search state.
  `dev.json`              saved per-plugin dev choices (name -> "upstream"
                          or a checkout path); see |dash-paq-dev|.

`vim.pack`'s own lockfile is not written by dash-paq.nvim except
through |:DashPaq-lock|; dashboard updates and cleans still change it
through `vim.pack`. It lives at
`stdpath("config") .. "/nvim-pack-lock.json"`.

14. Limitations                                         *dash-paq-limitations*

  - `vim.pack` is still experimental; its API can change between
    releases.
  - The dashboard calls no private `vim.pack` function; it parses the
    plain-text report `vim.pack.update()` opens in the
    `nvim-pack://confirm` scratch buffer. A future format change can
    silently break parsing until this plugin catches up.
  - Differences from lazy.nvim: see |dash-paq-spec-unsupported| and
    the startup model in |dash-paq-installation|.
